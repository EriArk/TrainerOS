# SDK group records — контракт для параллельной работы над Lobby

25 октября 2026. **Исходники и локальные проверки готовы, ещё не поставлено.** Владелец поручил этому чату
SDK и Brick Tanks на 16 игроков; Lobby меняется в другом чате.
Изолированная ветка SDK: `codex/sdk-group-records`, база `59625d6`.

## Граница изменений

Здесь: `src/platform/sdk/SdkNetwork.*`, capability в `PlatformHost`, чтение
`seats` из Crates activity manifest, тесты SDK, публичный `sdk/NETWORK.md`.
Не меняем LobbyCoordinator, LobbyRuntime, модель комнат, Social и QML Lobby.

## Вход из Lobby

- Режим остаётся `sdk.records.v1`. Игра объявляет **максимум** `seats: 16`;
  допустимы 2–16 готовых участников, заполнять все 16 мест не обязательно.
- `runtime` сохраняет `{app, protocol}`. Манифест Brick Tanks: `tanks.3`.
- `prepare(operation, context, done)` получает `lobby`, `generation`, `self`,
  `game`, `members`; `game.seats` совпадает с максимумом установленной игры.
  У играющих уникальные ID и места 1…16, `connected: true`. Наблюдатели
  исключены из игрового транспорта. Владелец комнаты должен занимать место.
- `launch(operation, ticket, state, done)` использует прежний ticket/фазы.
  `state.owner` — хост симуляции. Состав и места фиксированы на этот матч.
- `runtimeSignal` и `sendRuntimeSignal` должны маршрутизировать сигналы между
  владельцем и каждым из остальных игроков. Игровые пакеты через Fluxer не идут.
- Хост создаёт отдельную защищённую связь с каждым клиентом; клиент только
  с хостом. Прежний helper переиспользуется; новая тяжёлая серверная служба не нужна.
- Локальный launch ack возвращается после подключения всех нужных связей и
  регистрации приложения. `network.ready` приходит после общей фазы `playing`.
- Любое изменение игровых участников/мест/owner, потеря связи или выход
  заканчивают текущий матч, сохраняя обычный lifecycle комнаты. Нет тихой
  миграции хоста, mid-match join, автоперезапуска или переиспользования grant.

## Выход SDK для игры

Capability `network.group: 1`, предел `maxPlayers: 16`. Для группы событие
`network.ready.session` содержит `self`, `host`, `hostMember`, `members` (ID/seat),
`channels` (peer/channel), protocol/lobby/delivery/maxBytes/window. У клиента одна
связь; у хоста N−1. Send/consume/ack сохраняют отдельную последовательность и
кредит для каждого channel. Старое двухместное событие и API остаются совместимы.

## Проверки и передача

Полная Release-сборка `traineros` на Windows завершена. Qt 6.11.1 / GCC 16.1:

- [SDK network](evidence/sdk-group-20261025/network.txt): 5 passed, 0 failed.
  16 независимых участников с реальными TLS helper-процессами, подключение за
  7819 мс в этом прогоне. Проверены независимые кредиты, остановленный читатель,
  чужие grants, потеря участника и очистка, прежний двухместный запуск и новая сессия.
- [Crates](evidence/sdk-group-20261025/crates.txt): 4 passed, 0 failed.
  Installed seats 16, отклонение 1/17/дробного/строкового seats, live inventory.
- [Platform](evidence/sdk-group-20261025/platform.txt): 12 passed, 0 failed,
  1 skipped: внешний пакет Godot avatar отсутствует; его приёмка не заявляется.

Тесты используют локальный заменитель provider signaling. Это не 16 физических
устройств, не живой Fluxer и не интернет. До публикации основной чат объединяет
SDK с собственной работой Lobby, собирает ARM64 и проверяет цепочку установки,
выбора 2–16 мест, Ready/Start, реванша и возврата на целевых устройствах.
Копировать изменения Lobby из этой ветки не требуется: его исходники не изменены.

До 15 helper-процессов на хосте — явная цена повторного использования транспорта.
Память, запуск, upload, FPS и задержки на Odin/Flip требуют отдельного замера.
16 — продуктовый предел, а не обещание отсутствия лагов в любой сети.
