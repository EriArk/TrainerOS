# Покрытие требований картой структуры

**Снимок GitHub EriArk/TrainerOS: 21 октября 2026.** 253 issue: **243 открытых,
10 закрытых**; pull requests не входят. Номера #66/#67 отсутствуют в выдаче issues,
это не потерянные строки. Получено через `gh issue list --state all --limit 500`;
число открытых сверено с API репозитория. Таблица — полный индекс требований из
этого снимка, а не заявление о выполнении каждого acceptance checkbox.

Каждый issue ведёт к устойчивым R-ID [готовности](FEATURE_READINESS.md), основному
S-владельцу [структуры](STRUCTURE_MAP_RU.md) и F-цепочкам входа/выхода. У epic
перечислены несколько строк. Детальные условия остаются в самом issue и профильном
документе; краткое название здесь их не заменяет. Новые owner decisions имеют
приоритет над старым body и его очередью. Сверены заголовки/связи полного снимка и
детальные контракты пяти закрываемых пробелов; это не новый аудит каждого runtime.

**GitHub «открыт/закрыт» — состояние записи**, не фактическая готовность функции.
Её галочки находятся только в R-таблице. Исторические проверки не переименованы в
сегодняшнюю приёмку, superseded UX не возвращается в продукт. Issues здесь не
закрывались и не редактировались. Глобальная очередь отсутствует.

## Как сохранять полноту

При новом issue добавить строку и существующий либо новый R-ID. При разделении
функции сохранить старый ID за конкретной частью и связать остальные новые строки;
не перенумеровывать всю таблицу. Если решение заменено, написать чем, сохранить
неотменённые требования и checks. Не закрывать issue только из-за появления строки.
Обновлять обе карты и профильный контракт вместе с meaningful implementation.

Проверка этого снимка: набор issue ID совпадает с выгрузкой без повторов; все R/S/F
ссылки разрешаются; каждый R имеет одного основного владельца; обратная карта S→F
совпадает с участниками F. Это проверка полноты **ссылок и ответственности**, а не
доказательство исполнения всех требований.
