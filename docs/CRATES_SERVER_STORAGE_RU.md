# Crates — данные на VPS и безопасная установка

> Обсуждено 20 октября; сверка 21 октября 2026. Уточнение принятой модели #144/#146/#147/#148. **Каталог/установщик уже имеют ограниченную реализацию и поставку** ([CRATES76](CRATES76_INSTALLER.md), [CRATES77](CRATES77_CATALOGUE.md)); этот документ сам её не доставляет и не доказывает все внешние пакеты. Путь автора/релиза/отзыва — [F09](STRUCTURE_MAP_RU.md#f09); общие серверные границы — [Backend](TRAINEROS_BACKEND_PLAN_RU.md).

## 1. Где что лежит

| Тип данных | Место | Причина |
| --- | --- | --- |
| Ручная структура Crates, редакционные подборки, проектные описания | Исходники/проверенные манифесты; опубликованная компактная копия на VPS | Один авторитетный каталог без GitHub-сканирования клиентов |
| Версия, список релизов, платформа/архитектура, зависимости, checksum, лицензия, автора и ссылки | VPS, с проверенным источником истины в релизном процессе | Быстрая delta-синхронизация |
| Маленькие обложки/иконки/миниатюры | VPS или надёжный статический хост, по мере необходимости и с лимитами размеров | Не нужно поднимать полноценный CDN с первого дня |
| Совместимые конфиги, шаблоны, настройки для runtime/адаптеров | VPS как **данные**, проверенные, с версией, хешем и допустимой областью применения | Возможность поправить небольшой профиль без пересборки бинарника, когда формат уже поддержан |
| Декларативные **рецепты установки** | VPS, в versioned manifest | Установщик знает источник, зависимости и допустимые действия |
| Исполняемые игры, приложения, системные модули, большие игровые ресурсы | **Утверждённые GitHub Releases** | Не расходуем место и трафик VPS на пакеты |
| Особые исполняемые установочные скрипты, если действительно нужны | **Проверенный версионированный пакет релиза**, с review/целостностью и ограниченным исполнением | **Нельзя исполнять произвольную команду, скачанную с API** |
| ROM/BIOS, личные сохранения, учетные секреты/закрытые переписки | **Не на сервере Crates** | Принадлежат пользователю; сохранить существующие права и ограничения |

Это расширяет использование небольшого хранилища для конфигураций и **не отменяет** запрет на самодельное зеркало архивов.

## 2. Публикация и обновление каталога

Сохранить решения [#144–152](https://github.com/EriArk/TrainerOS/issues/144):
- Витрину Crates и расположение её объектов автор редактирует вручную через repo/Codex. Никакого самостоятельного автоматического сканирования чужих GitHub-репозиториев для пополнения каталога.
- **Один логический sync при открытии Apps → Crates:** клиент передаёт последнюю ревизию/ETag/cursor, получает только изменившиеся проекты, версии, размещение и снятые публикации. Пустое изменение — маленький ответ. Офлайн — последний кеш.
- **Никакого автоматического Download, Update или Update All** при просмотре/синхронизации. Эти действия запускает только пользователь и обслуживает один общий Downloads.
- Впервые одобренный автором проект получает стабильную идентичность; новые GitHub Releases этого проекта публикуются через **контролируемый авторский workflow** без второй кнопки «одобрить релиз».
- Клиент **не опрашивает GitHub API** ради проверки новых версий; при явно выбранной установке скачивает пакет **напрямую из разрешённого GitHub Release URL**.
- Старые утверждённые версии остаются доступны для ручного выбора/отката; установка одной версии не удаляет чужие сохранения.
- Удалённый каталог может снять/отозвать описание небезопасного релиза, но **не удаляет самостоятельно** уже установленное приложение пользователя.

## 3. Рецепты вместо произвольных shell-скриптов

Нужен маленький **типизированный декларативный манифест**, который задаёт **что** и **с какими проверками** требуется сделать. **Как** именно это исполнять, решает существующий проверенный установщик TrainerOS.

Пример логики рецепта (иллюстрация, не утверждённый JSON/SDK contract):
1. Выбрать подходящий релиз по проверяемой архитектуре/host/runtime.
2. Запросить резервирование места и поставить задачу в **общую Downloads**.
3. Скачать утверждённый artifact с GitHub Releases, проверить размер, checksum, подпись и права распространения.
4. Проверить безопасные пути архива и допустимые зависимости; распаковать только в разрешённую установщиком область.
5. Применить совместимый конфигурационный профиль / зарегистрировать игру, приложение или модуль **через существующие API TrainerOS**.
6. Зафиксировать версию и возможность отката; показать результат в **общем Downloads**.

**Безопасность:** никаких полей вида `sudo_command`, `post_install_shell` или URL к неограниченному скрипту, полученному с сервера. Нельзя пропускать проверки потому, что запрос пришёл от «своего VPS». Данные конфигураций также проверяются на допустимые пути, формат, версию, влияние на сохранения и владельца.

Если специальная установка не выражается допустимыми действиями штатного установщика, её код следует включить в **аудированный подписанный/проверенный пакет на GitHub Releases**, а не выполнять новое содержимое URL с привилегиями. Реализация специальных привилегированных шагов проходит существующие проверки trust boundary и rollback.

## 4. Маленькие обновляемые данные

Без пересборки всей игры иногда можно обновить:
- Метаданные, обложку, текст, сведения о зависимости или совместимой версии.
- **Версионированные профили запуска** и параметры допустимых адаптеров, **только** если рантайм уже умеет эти данные читать.
- Поддерживаемые шаблоны настроек и необходимые небольшие статические файлы с авторством, хешем и разрешённой областью применения.

Нельзя удалённым JSON в обход пользовательского согласия переписывать играющие процессы, файлы сохранений или менять бинарный код. Если обновление требует нового кода, отправлять новый релиз и ждать **явного Update**.

## 5. Схема каталогов (пример организации, не команда создания)

На VPS можно логически разделить:
- **catalog/** — проверенные снапшоты и delta ревизии каталога.
- **manifests/** — метаданные версий и рецепты.
- **assets/** — ограниченная статика.
- **profiles/** — совместимые конфигурационные файлы/шаблоны.
- **database/** — служебная БД, отдельно от публичной статики.
- **backups/** — только локальный кратковременный рабочий слой; **настоящие backups должны находиться вне VPS**.

Точный layout и API маршруты — технические решения будущей реализации; не путать с публичными URL и не публиковать каталоги с секретами.

## 6. Нагрузка и надёжность

- Пока сервер **не хранит большие пакеты**, объём данных должен быть небольшим, и VPS с условными **80–160 ГБ SSD** имеет хороший стартовый запас; это не обещание вместить любое число полноразмерных скриншотов/записей.
- Протоколы manifest и delta имеют ограничения размера, кеширование, сжатие при поддержке, ETag/cursor, повторяемое применение и атомарный rollback опубликованной ревизии.
- Публичная статика и конфигурационные шаблоны не должны разрешать доступ к закрытым служебным файлам.
- Следить за ростом, хранить внешние резервные копии и проверять restore на тестовом окружении.
- Публикация метаданных не должна запускать массовое скачивание у клиентов. При проблемах API Crates показывает локальный кеш, а установленные игры продолжают работать.
