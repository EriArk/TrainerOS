## 3. Текущая иерархия документации

1. **[PRODUCT_ARCHITECTURE_RU](PRODUCT_ARCHITECTURE_RU.md)** — короткий продуктовый каркас, владелец и границы системы; только утверждённый **target**.
2. **Feature issues GitHub** — конкретный современный контракт и актуальные owner addenda. Более позднее решение владельца исправляет общий каркас, а не наоборот.
3. **[ROADMAP](ROADMAP.md) + [CURRENT_TASKS](CURRENT_TASKS.md)** — порядок независимых работ и remaining acceptance, не хроника свежих идей.
4. **[PROJECT_STATUS](../PROJECT_STATUS.md) + [CHANGELOG](../CHANGELOG.md)** — снимки реально доставленного и датированная история. Не подменяют код/установку датой сегодняшнего чтения.
5. **[ARCHITECTURE](ARCHITECTURE.md), [DEVELOPMENT_WORKFLOW](DEVELOPMENT_WORKFLOW.md), технические docs** — детали реализации и проверки, с датой/версией.
6. **Old PRODUCT_SPEC / PRODUCT_VISION / UX map / expansions / archived AGENTS** — прежние обязательства и доказательства, но только в непротиворечащей части.

**Статусы должны разделяться:** `TARGET` — утверждено; `CODE` — есть в источниках; `INSTALLED` — установлено на конкретном устройстве; `TESTED` — проверено указанным методом; `OPEN` — недостающая приёмка. Не менять один статус на другой по наличию кнопки или закрытого issue.

## 7. Как не повторить накопление

- **Один владелец на каждую концепцию.** В другом документе — короткий pointer, а не копия того же контракта.
- **Датировать изменения и их доказательства.** Современная схема продукта и old build — не одно и то же.
- **Сначала пользовательский сценарий, потом кодовый слой.** Не создавать новый framework ради архитектуры, если хватает существующего API.
- **Изменять только связанный блок.** Бета, транспорт Fluxer, SDK и визуальный redesign имеют разные acceptance.
- **README для обычного человека**, AGENTS для исполнения, issues для требований, evidence docs для фактов. Не сваливать всё в одну простыню.
- **Минимум внутренней бюрократии.** Platform SDK #235 ориентирован на доступные возможности, не на систему запретов. Обычная Linux-программа не обязана получать новый «пропуск TrainerOS».

**Результат аудита:** текущая точка входа и большинство опасных верхнеуровневых противоречий исправлены; исторический массив сохранён. Далее обновлять техническую документацию **вместе с конкретной реализацией**, а не массовым поиском/заменой исходников или прежних проверок.
