# TrainerOS — действующий каркас продукта и архитектуры

**Продуктовый контракт от 19 октября 2026 года, дополнен 20 октября.** Это компактная карта **согласованного направления**, а не отчёт об установленной версии. Исходный код в `main` и [PROJECT_STATUS](../PROJECT_STATUS.md) подтверждают только реально выполненное; [CHANGELOG](../CHANGELOG.md) хранит историю. Вопросы исполнения и точные acceptance — в [issues](https://github.com/EriArk/TrainerOS/issues), [ROADMAP](ROADMAP.md) и [CURRENT_TASKS](CURRENT_TASKS.md).

> **TrainerOS — самостоятельная controller-first игровая пользовательская среда поверх Linux, а не только frontend эмуляторов.** ОС должна давать консольную простоту без необходимости переходить в Desktop Mode для обычных компьютерных действий. Linux, Steam и maintenance desktop остаются доступными, но не являются обязательными остановками пользовательского сценария.

## 1. Навигация и роли

**Ровно пять основных L1/R1-разделов:**

| Раздел | Смысл и вторичные поверхности |
| --- | --- |
| **Home** | Личное игровое пространство, выбранная игра, продолжение, статус/контекст, доступ к текущей деятельности |
| **Games** | Платформы, коллекции, библиотека, несколько представлений; Y открывает общие Recent Games/Favorites |
| **GameHub** | Контекст конкретной игры: **Overview → RetroAchievements → Adapter (только при наличии) → Lobby** по L2/R2; Timeline/Screens — внутри Overview; специальные действия — внутри Adapter |
| **Social** | **Messages → Communities → Discover** по L2/R2; чаты, друзья, группы, голос, присутствие, связи с играми |
| **Apps** | **Apps → Crates → Browser → Files** по L2/R2; полноценные Linux-приложения, общая файловая среда, загрузки и устанавливаемые дополнения |

Никакие установленные модули не создают шестой primary. Внутренние экраны, инструменты и контекстные действия разрешены в предусмотренных местах. Ранее существовавшие «Pokémon Companions / Trainer» как отдельные основные разделы и старое расположение OddCrate/Store заменены; исторические документы сохраняют свидетельства прежнего каркаса.

### Физическое управление

- **L1/R1** — основные разделы; **L2/R2** — разрешённые соседние представления активного раздела (с учётом модалей и контекста).
- **X** — глобальный Quick Apps dock **в оболочке**, **Y** — глобальные Recent Games/Favorites **в оболочке**. В живой игре кнопки принадлежат игре, если ОС явно не открыла защищённую системную поверхность.
- **Select** — локальное контекстное действие выделенного объекта; отдельные внутренние Browser/Files назначения оговариваются их UI-контрактами. Долгая A может открывать истинное контекстное меню там, где поддержано.
- **Физическая Home** открывает **Shell Options** вне игры или **Game Options** для фактически запущенной игры. Контекст выбранной в библиотеке игры нельзя подменять контекстом текущего PID/сессии.
- **Start** в оболочке открывает двухчастный виджетный dashboard **QuickActions / Extensions**. Во время игры native Start остаётся игре; после открытия Game Options физической Home нажатие Start открывает тот же dashboard поверх Game Options. Game Options не содержит системные Power/Settings/launcher icons — они находятся в Shell Options.
- Из Home/Game Options и приложений должны работать корректные возврат, сворачивание и восстановление фокуса; открыть Home ≠ остановить игру или автоматически её сохранить. Явный Exit использует существующие защищённые процедуры.

**Ссылки на актуальное целевое поведение:** [#111](https://github.com/EriArk/TrainerOS/issues/111), [#206](https://github.com/EriArk/TrainerOS/issues/206), [#224](https://github.com/EriArk/TrainerOS/issues/224), [#233](https://github.com/EriArk/TrainerOS/issues/233), [#168](https://github.com/EriArk/TrainerOS/issues/168), [#170](https://github.com/EriArk/TrainerOS/issues/170), [#227](https://github.com/EriArk/TrainerOS/issues/227).

## 2. Системные владельцы и границы

| Система | Чем владеет | Чего не делает |
| --- | --- | --- |
| **Shell / Navigation** | Основные маршруты, кнопки, фокус, оверлеи, ошибки и UI-хост | Не позволяет расширению захватить системные вкладки/кнопки |
| **Game Session / Runtime** | Реальный запуск, ввод, Game Options, minimize/return, безопасный Exit, проверка возможностей | Не смешивает выбранную игру с запущенной; не выдумывает поддержку NetPlay |
| **Games / GameHub** | Идентичность игры, коллекции, обзор, подтверждённые сведения, поддерживаемые игровые действия | Не требует семантического адаптера ради обычного запуска |
| **Experience Adapter** | Специфические для игры экраны, предметы, прогресс и допустимые операции | Не владеет файловой системой, универсальным Lobby, RA и правом записи save |
| **Social / Fluxer** | Аккаунт общения, переписки, контакты, группы, звонки, приглашения, presence | Не становится центральным владельцем всех локальных игр или сохранений |
| **Lobby** | Единая комната, участники, места, Ready, admission, выбранная игра/режим, переходы и rejoin | Не создаёт отдельных NetPlay/Remote Play мастеров или вторую систему комнат |
| **Apps / Files / Downloads** | Обычные программы, файловые операции/провайдеры и единый список длительных задач | Не запускает второй файловый менеджер или очередь загрузок для каждого приложения |
| **Crates** | Ручные подборки, каталог, версии и намеренные установки/обновления через общую очередь | Не является обязательным магазином для всех Linux-программ или шлюзом к SDK |
| **Platform adapters** | Фактически доступные функции Armada; позднее SteamOS/Bazzite через capability-gates | Не эмулируют неподдерживаемые драйверы и не подменяют host update |

Игра может запускаться через RetroArch, standalone emulator, Steam или как native app. Runtime отвечает за исполнение; **игра, пользователь и текущая сессия — отдельные сущности**. Стандартные сохранения остаются у пользователя. Любое семантическое изменение точного save/build проходит через существующий защищённый host transaction, а не прямую запись расширения.

### TrainerOS Account и собственные эксклюзивы (TARGET)

**[Согласованный концепт аккаунтов, экономики и эксклюзивов](TRAINEROS_ACCOUNT_ECONOMY_RU.md)** (20 октября 2026): локальный Trainer остаётся самостоятельным и офлайн; отдельный переносимый **TrainerOS ID** хранит права на единый кошелёк и приобретённую косметику. Fluxer — внешний провайдер входа и общения, RetroAchievements — подтверждённые достижения, Patreon/Ko-fi — источники подписочных преимуществ. Нового собственного пароля/обязательного облачного аккаунта для обычного запуска или сторонних SDK-программ нет.

**Магазин косметики доступен бесплатно всем.** Одна валюта зарабатывается проверяемой игрой/достижениями; действующая подписка увеличивает заработок **до ×3**, старшие уровни могут открывать dev/beta-сборки. Покупки сохраняются после отмены подписки; скидки и фиксированные ежемесячные раздачи монет не входят в актуальную модель. Баланс и тарифы ещё требуют исследования.

**Собственные игры AbyssTail — эксклюзивы TrainerOS за счёт платформенной интеграции**, а не искусственного DRM: игровые механики остаются в самой игре, а аккаунты, кошелёк, Social, Lobby, общие награды и другие действительно используемые функции предоставляются TrainerOS. Это не ограничивает сторонние игры, эмуляторы и свободный Platform SDK. Описанное — архитектурное направление, не утверждение об уже реализованных функциях.

## 3. Platform SDK — открытая интеграция, а не новый запретительный режим

**Утверждённая концепция, пока не готовый публичный SDK:** [#235 — Platform SDK & Network Fabric](https://github.com/EriArk/TrainerOS/issues/235); подробные задачи [#236–244](https://github.com/EriArk/TrainerOS/issues/235).

Логически два независимых интерфейса:

- **Service Registry:** находить доступные возможности Network, Social, Lobby, Gaming, Files/Downloads, Media, Device и Lifecycle/events.
- **Contribution Registry:** необязательные вложенные страницы, Game Tools, контекстные команды, Start widgets, Shell/Game Options additions и безопасные HUD/overlays в существующем UI.

**Роли программ, а не отдельные обязательные форматы:** game, Linux app, system extension, game tool, semantic Experience adapter, file/media/service provider. Один пакет может совмещать роли. Простой виджет или P2P-игра не должны реализовывать десять ненужных протоколов.

### Свобода по умолчанию

- Никаких новых разрешений за обычные окна, свои файлы, обычную сеть, собственный геймпад, корректную регистрацию разрешённой UI contribution.
- **Никакого обязательного Crates**, отдельной учётной записи, сервера разработчика или процедуры одобрения SDK для локальной установки и базовых сервисов.
- Осмысленные проверки **на настоящих границах доверия**: чужие файлы/профили/личные переписки, микрофон, камера, захват, системные привилегии и защищённая запись в saves. Согласие пользователя на выбор файла/сессию не повторять для каждого байта.
- Установленные дополнения не исполняют произвольный непроверенный QML/native код внутри процесса shell. Изоляция и восстановление — там, где риск реален.
- Не проксировать любой сетевой пакет через глобальный посредник, если стороны уже получили подходящий защищённый канал.
- Не создавать вторые менеджеры сервисов, системы прав, установщики или глобальные БД ради красивых абстракций. SDK должен быть легко подключаемым **по частям**.

Реестр и разрешения — описание и доступ к работающим системным механизмам, **не административная бюрократия**. #231 продолжает владеть ограниченным SPI system modules, #92/#207 — семантическими game adapters; #233 — UI виджетов, #144–152 — распространением.

## 4. Network Fabric и Fluxer: преимущественно без серверов приложений

Каждое устройство может быть узлом: локальные данные и вычисления остаются у пользователя. Подключение осуществляется через LAN/nearby/direct P2P, а существующий Fluxer помогает с идентичностью, контактами, приглашениями, сигналингом и разрешёнными сообщениями.

**Control plane ≠ data plane.** Небольшие асинхронные события и realtime-пакеты имеют разные требования. Голосовые/видеосерверы Fluxer **не считать автоматически** произвольным app-data relay: пригодность, правила сервиса, rate/latency, data channels и доступность проверяет уже существующая [#105](https://github.com/EriArk/TrainerOS/issues/105). Если прямой P2P не проходит NAT и нет доказанного relay — показать ограничение, а не обещать подключение.

Для сторонних программ Network Fabric даёт минимальные peer/session/channel/events primitive. Маленький Tetris не требует своего backend, но сам определяет правила игры и синхронизацию; TrainerOS не вводит универсальную серверную симуляцию, CRDT или античит.

**Social Activities:** установленная игра/программа может запускаться из DM/группы, использовать тот же **GameHub Lobby**, возвращать участников к переписке и сохранять ссылку на постоянную активность. Постоянная ссылка не означает постоянно работающий мир. Owner-scoped shared objects и remote services **не обязательны** для простых игр; хранение у владельца, результаты у участников, операции и подтверждения определяются реальной задачей.

**Релевантные задачи:** [#238](https://github.com/EriArk/TrainerOS/issues/238), [#239](https://github.com/EriArk/TrainerOS/issues/239), [#240](https://github.com/EriArk/TrainerOS/issues/240); существующие [#179](https://github.com/EriArk/TrainerOS/issues/179)/[#216](https://github.com/EriArk/TrainerOS/issues/216) остаются каноническими владельцами Lobby.

## 5. Поставка, поддерживаемые платформы, статусы

- **Сейчас:** исходники + проверенная разработческая установка на поддержанных ARM-портативках, но **не выпущенная публичная готовая ОС**. Последний коммит `main`, который проверен при составлении этого документа: `7c009266` от 14 октября 2026.
- **Ближайшая цель:** публичная ранняя бета после самостоятельных требований по install/update/recovery и безопасному игровому циклу. Новые SDK issues #235–244 — архитектурный foundation/backlog, **не автоматически новый блокер беты**.
- **ArmadaOS:** первоочередной host с подтверждением конкретного устройства и API.
- **SteamOS/Steam Deck и Bazzite:** позже интеграция в существующую систему; Steam, host updater и maintenance desktop не удаляются без специального подтверждения.
- **Crates:** ручное курирование, явные Download/Update/Update All, артефакты релизов и общий Downloads; не автоматическое обновление с сервера владельца.

**Метки доказательств в документах:** `TARGET` (утверждённое поведение), `CODE` (есть в `main`), `INSTALLED` (установлено на названном устройстве), `TESTED` (конкретная проверка), `OPEN` (зависимость или оставшаяся приёмка). Одно не доказывает другое. Не заполнять их задним числом по плану или закрытому issue.

## 6. Канонический маршрут работы с документацией

1. **Этот документ** — текущая продуктовая карта и действующие границы.
2. **[GitHub issues](https://github.com/EriArk/TrainerOS/issues)** — детальные актуальные согласованные контракты конкретных функций, более поздние уточнения владельца.
3. **[ROADMAP](ROADMAP.md) / [CURRENT_TASKS](CURRENT_TASKS.md)** — очередность, зависимости и фактические незакрытые критерии; не выбирать работу из старого «next» в хронологических отчётах.
4. **[PROJECT_STATUS](../PROJECT_STATUS.md) / [CHANGELOG](../CHANGELOG.md)** — доставленные результаты, точные проверки и история.
5. **[ARCHITECTURE](ARCHITECTURE.md) / [DEVELOPMENT_WORKFLOW](DEVELOPMENT_WORKFLOW.md)** — кодовые границы и процесс, но их старые датированные разделы не отменяют решения 15–19 октября.
6. **[PRODUCT_VISION_RU](PRODUCT_VISION_RU.md), [PRODUCT_SPEC](PRODUCT_SPEC.md), [UX_NAVIGATION](UX_NAVIGATION.md), [UX_OPTIONS_MAP_RU](UX_OPTIONS_MAP_RU.md), [CODEX_START](CODEX_START.md)** — подробные первоначальные требования/исторические срезы; применять только непротиворечащие современные части.

**Приоритет при конфликте:** новое явное решение владельца → актуальный feature-issue/этот общий контракт → активная очередь работ → действующее реализационное доказательство → старый target/history. Это **не означает**, что целевое решение уже находится в коде. В отсутствие решения не выдумывать поведение; поднять конкретный конфликт, обновить владельца контракта и ссылки, не переписывать весь архив.

Не объединять все исторические спецификации в один огромный документ; обновлять первую каноническую точку входа и короткие указатели. Дальше использовать [индекс документации](README.md).
