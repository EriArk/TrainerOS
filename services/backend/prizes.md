# Постоянные призы

Политика `prizes-2026-10-v1`, миграция `0011_prizes.sql`. Владелец — существующий
Economy/Accounts (S11), отдельного сервиса нет. Призы не меняют XP и Искры.

- Каждый достигнутый уровень начиная со 2 даёт неизменяемое право на одежду.
  На уровнях 3, 6, 9… дополнительно выдаётся постоянный слот полного образа.
  Стартовый уровень 1 ещё требует решения владельца. Существующие уровни
  догоняются при чтении аккаунта/инвентаря; лимит 16 платных предложений
  не ограничивает число наградных слотов.
- `outfit_slots` объединяет права из покупок и наград. Миграция переносит
  существующие права, сохраняет рецепты и историю покупок. Запись/переключение
  прежние; наградный слот не списывает Искры.
- `prize_grants` — неизменяемые факты с владельцем, уникальным основанием,
  временем, игрой/уровнем и версией политики. Общая блокировка аккаунта
  сериализует начисления/покупки/догоняющую выдачу.
- `prize_catalogue` пока пуст: нет назначенных моделей призов. Уровневое право
  `level.N` сохраняется без ресурса; интерфейс честно показывает подготовку вещи.
  Назначение предмета конкретной игре через каталог позволяет выдать его при
  следующей синхронизации уже подтверждённого прохождения. Клиент не назначает
  каталог, источник, уровень, XP или награду.

## Подтверждение прохождения

Существующая привязка RA проверяет неизменяемый ULID и право на аккаунт.
Сервер сам читает [GetUserAwards](https://api-docs.retroachievements.org/v1/get-user-awards.html):
`Game Beaten` даёт трофей прохождения, `Mastery/Completion` — отдельную отметку
полного набора, hardcore — дополнительное отличие. Это разные факты одной игры,
на полке они объединяются. Console 100/101 не принимаются.

Для явно запрошенных игр [GetGameInfoAndUserProgress](https://api-docs.retroachievements.org/v1/get-game-info-and-user-progress.html)
также подтверждает скрытые в публичном списке результаты: все `progression`
и хотя бы одна `win_condition` (если они есть), непустой набор таких условий,
только основной набор без `ParentGameID`. Полный набор достижений не подменяет
прохождение сюжета. Softcore/hardcore учитываются отдельно. Правило соответствует
[RA progression/win guidelines](https://docs.retroachievements.org/guidelines/content/progression-and-win-condition-guidelines.html).

Старые подтверждённые результаты восстанавливают косметические факты, но не
дают задним числом XP/Искры; денежная политика и дата привязки остаются прежними.
Пустой список локальных игр не мешает импорту публичных наград. Отсутствие/скрытие
награды при следующем запросе не отзывает прежнее право. Будущие даты пропускаются.
Неподтверждённые локальные отметки/сохранения, Crates и другие источники пока не
выдают призы. Правила не объявляют универсальную поддержку всех ретроигр.

## API и представление

- `GET /v1/me/prizes?before=<sequence>`: 100 фактов за страницу, следующие
  три уровня, пять выбранных экспонатов, число ожидающих наград и первые
  100 непоказанных прав для ограниченного вручения.
- `POST /v1/me/prizes/seen {ids:[uuid]}`: отмечает только перечисленные права
  текущего владельца. Повтор безопасен; чужие UUID не открывают данные.
- `PUT /v1/me/prizes/shelf {games:[id]}`: не больше пяти разных принадлежащих
  игроку трофеев. Сохранение сериализовано; последняя явная запись побеждает.

Для всех маршрутов нужен существующий bearer-сеанс. Публичного grant API нет.
Runtime не может менять/удалять выданные факты или редактировать каталог.
Показ, «Позже», отсутствие одежды и офлайн не отменяют выдачу. Публичная проекция
для друга и настройки видимости остаются следующим незавершённым шагом.

## Обновление и откат

Перед миграцией — существующий закрытый backup БД. Старый образ со схемой 10
не совместим со схемой 11: проверка readiness отвергнет историю миграций;
его нельзя просто запустить как откат. Исправлять код поверх схемы 11 либо
в отдельном обслуживании восстанавливать согласованную пару образ/backup,
учитывая выданные после backup права. Не удалять новые призы для отката интерфейса.
Клиентские обновления сохраняют прежние профили, рецепты и общие avatar assets.
