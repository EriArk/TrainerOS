# TrainerOS Backend — серверный каркас

25 октября 2026. Общая основа реализована в `trainer_backend/`, развёртывание —
`deploy/compose.yaml`. По последнему указанию владельца сборка, PostgreSQL и
runtime-проверки выполняются на существующем сервере. Рабочий компьютер хранит
исходники; временные базы и окружения сборки там больше не нужны.

Позднее 25 октября добавлен [модуль Accounts](accounts.md): Fluxer-only identity,
подтверждение входа кодом, OAuth/PKCE и собственные сессии. Код установлен, но
provider login включён с отдельным приложением владельца и HTTPS callback.
Живые consent/cancel/relogin, refresh и отзыв временных серверных сессий проверены.
[Результаты](../../docs/evidence/backend-oauth-live-20261025/README.md).
Обязательный ручной код не принят как обычный пользовательский сценарий:
безопасный возврат в native shell и SDK integration остаются открытыми.

## Реализовано

- FastAPI: `/health/live`, `/health/ready`, `/v1/capabilities`, фактический OpenAPI.
- PostgreSQL: явная миграция с контрольной суммой и advisory lock, ограниченная
  runtime-роль, отдельная maintenance-команда. Запуск API не меняет схему.
- Команда, квитанция, аудит и её эффекты в одной транзакции. Повтор с тем же
  operation ID возвращает квитанцию; другой payload даёт конфликт.
- Очередь: конкурентный захват, lease/fencing, ограниченные повторы и dead letter.
  Завершение просроченной задачи не фиксирует эффекты старого исполнителя.
- Outbox: постоянный индекс событий, dedup после удаления payload, атомарное
  применение и acknowledgement. `latest` только для заменяемого состояния;
  счётчики используют `all` и собственные правила порядка.
- Docker Compose: закрытая сеть БД, API только на loopback сервера, ограничения
  памяти/CPU/PID, ротация логов, непривилегированный read-only API/worker,
  runtime получает только свой DSN-файл. Секреты не попадают в Git.

## Что ещё не работает

В установленной конфигурации объявлены только `accounts.fluxer_login` и
`accounts.sessions`; базовый запуск без OAuth overlay отключает их.
13 владельцев модулей зарегистрированы;
профили, результаты, рейтинги, турниры, кошелёк, магазин и остальные провайдеры
ещё не реализованы. Worker не имеет игровых обработчиков
и не подтверждает неизвестные задания. [67 операций проекта](contracts/README.md)
не объявляются целиком работающим API. Реализованные auth/session routes указаны
в [Accounts](accounts.md) и фактическом OpenAPI. `Principal` — внутренний тип
доверенного кода, не клиентское поле. Доменные обработчики обязаны проверять
собственные разрешения и инварианты.

Текущие handlers выполняют короткие транзакционные эффекты в БД. Изолированные
долгие валидаторы и внешние побочные действия требуют отдельного исполнения и
протокола фиксации. Тесты не подтверждают античит, интернет-игру или нагрузку
16 игроков. SDK, аватар, игры, Lobby UI и бот этим пакетом не меняются.

## Серверная сборка и запуск

Работать из выделенного каталога сервиса, не из каталога другого проекта.
`deploy/images.env` фиксирует проверенные digest Python/PostgreSQL. Точные
зависимости находятся в `runtime-lock.txt` и `test-lock.txt`; версия `0.0.1`
служит внутренним номером пакета, не публичным релизом TrainerOS.

При первой установке создать закрытый каталог `deploy/secrets` (0700):
`owner-password` — случайный пароль владельца новой БД; `runtime-dsn` — libpq DSN
`host=db dbname=traineros_backend user=backend_runtime password=...` с независимым
случайным паролем. Файлы доступны контейнерному UID на чтение, каталог доступен
только оператору. Не выводить их и не передавать через аргументы команд.
Скопировать `deploy/images.env` в `deploy/.env`.

```sh
cd deploy
docker compose build api
docker compose up -d --wait db
docker compose --profile maintenance run -T --interactive=false --rm migrate
docker compose up -d --wait api worker
curl -f http://127.0.0.1:19120/health/ready
```

БД не публикует порт хоста. Выделенный HTTPS ingress публикует `/v1/*` и
`/health/live`; readiness/OpenAPI остаются внутренними. Шаблоны и условия
активации OAuth описаны в [Accounts](accounts.md). Учётная запись владельца доступна только
PostgreSQL и maintenance-контейнеру; приложение не может менять схему, principals,
историю миграций или уже записанный аудит. Миграция при обновлении — явный шаг;
перед следующими изменениями схемы сделать backup. Откат кода не означает откат
данных: сверить совместимость предыдущего образа и текущей схемы.

## Проверки на сервере

Read-only проверка внешних маршрутов: `python3 deploy/check-public.py https://traineros-api.abysstail.art`.
После активации OAuth добавить `--accounts`; это проверяет конфигурацию/отказы,
а не живой provider round trip. Старый `check-server.py` намеренно проверяет
foundation-only с остановкой БД/перезапуском API: не запускать его на активных
пользовательских сессиях и не использовать как обычный health check.

```sh
. deploy/images.env
docker build --build-arg PYTHON_IMAGE="$PYTHON_IMAGE" --target test \
  -t traineros-backend-test:oauth-live-20261025 .
docker run --rm --network none --cpus 1 --memory 768m --pids-limit 128 \
  traineros-backend-test:oauth-live-20261025
```

Тестовый контейнер создаёт собственную PostgreSQL под непривилегированным
пользователем, со случайными учётными данными; сервисная БД и её volume не
монтируются. Проверяются права, rollback, повтор/конкуренция команд, отзыв principal,
lease/fencing/retry, доставка событий и настоящие HTTP handlers. Тестовая БД
останавливается и удаляется, контейнер запускается с `--rm`.

## Backup и границы эксплуатации

`sh deploy/backup.sh` создаёт закрытый custom-format dump и SHA256 на сервере.
Из `deploy/`: `sh restore-check.sh backups/<имя>.dump` восстанавливает его в
одноразовый контейнер без сети и постоянных томов; рабочую БД не изменяет.
Проверяется восстановление foundation schema/migration history. Это не проверка
восстановления пользовательских сценариев, которых ещё нет.

Автоматическое расписание, шифрованная копия вне сервера, сроки хранения,
оповещения, ротация секретов и восстановление реальных account/economy данных
ещё требуют реализации/приёмки. `health/ready` проверяет доступность БД и точную
историю миграций, а не готовность продуктовых функций. Ближайшее условие Accounts —
отдельное приложение владельца, HTTPS callback и живой provider cycle, затем
интеграция с оболочкой/SDK и потребителями.
