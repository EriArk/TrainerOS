# Опыт и Искры: первая работающая цепочка

28 октября 2026. `account.progression` расширяет существующие Accounts;
отдельного аккаунта или локального кошелька нет. Это начисление и чтение прогресса,
**не вся Economy v2**. Постоянные сцены добавлены в [покупках](purchases.md),
расчёт поддержки описан ниже; активация поддержки и торговля ещё не реализованы.

## Первая настройка баланса

Владелец разрешил выбрать приблизительные суммы и XP с последующей корректировкой.
Политика `sparks-2026-10-v1` — расчётный старт, не статистика RA-пользователей:
ориентир 3–5 часов в неделю и 6–12 обычных достижений. Нет наград за таймер,
ежедневный вход, победы Crates, импорт сохранения или клиентские заявления.

| Событие | Опыт | Базовые Искры |
| --- | ---: | ---: |
| Проверенное достижение | 10 + 4 × min(RA points, 50) | 5 + 2 × min(RA points, 50) |
| Полный основной набор достижений | 500 + 4 × min(сумма points, 1000) | 250 + 2 × min(сумма points, 1000) |

Полное закрытие набора даёт **дополнительную** награду. Это точное первоначальное
значение completion для данного обработчика; прохождение только сюжета и игры
без RA не выдаются за реализованное определение полного прохождения.
Standard и Hardcore одного достижения не дают две награды. Увеличение сложности
или изменение ставки не переписывает уже выданные суммы.

Первый уровень начинается с 0 XP. Переход с уровня L требует `300+100×(L−1)` XP;
общий порог уровня L — `50×(L−1)×(L+4)`. Уровни 2/5/10/20: 300/1800/6300/22800 XP.
Набор из 30 достижений по 5 points даёт суммарно 2000 XP и 1000 Искр, уровень 5.
Это позволяет получить первые уровни за несколько вечеров, последующие — медленнее.
Mastery не тратится, не покупается и не зависит от поддержки. Позже владелец выбрал
250 Искр для трёх новых [сцен профиля](purchases.md); остальные цены и тарифы не выбраны.

## Доверие и привязка

Публичная выдача RA по нику не доказывает владение аккаунтом. В профиле игрок явно
включает награды, затем помещает одноразовый код в Motto своего RA-профиля и
подтверждает. Backend читает его через официальный Web API; стабильный ULID
однократно связывается с текущим TrainerOS ID. Код действует 30 минут, после
подтверждения его можно убрать. Один RA ULID нельзя присвоить другому TrainerOS ID
через выход, новое устройство или повторный вход. Восстановление/перепривязка
требует отдельной процедуры и здесь не реализована.

Используется собственный Web API key игрока из существующих RA Settings.
Он передаётся по HTTPS только после явного включения, не сохраняется на Backend,
не выдаётся в QML/SDK и не попадает в журнал. Эмуляторный login/token не используется
как серверный обход Web API. Provider читает profile/progress напрямую; клиент
передаёт только ограниченный список ID игр, не награды, суммы или даты.

Награды допускаются за подтверждённые RA события **после привязки**; начальная
загрузка старой истории не является массовым начислением. Для completion все
основные цели должны быть получены, последнее достижение — после привязки.
Untracked/неподходящий статус профиля, неполный ответ, неверная дата/идентичность
не подтверждают награду. Используются только основные наборы API; определения
триггеров не сохраняются и не распространяются. Это доверие RA как источнику,
не доказательство аппаратной аттестации или всех verified-session свойств #94.

Источники контракта: [RA Profile](https://api-docs.retroachievements.org/v1/get-user-profile.html),
[RA Game Progress](https://api-docs.retroachievements.org/v1/get-game-info-and-user-progress.html),
[#262](https://github.com/EriArk/TrainerOS/issues/262).

## Хранение и API

Миграция 0007 добавляет account projection, неизменяемую привязку, временный
challenge и append-only reward ledger. Runtime-роль не может UPDATE/DELETE журнал.
Уникальность `(RA ULID, source, event ID)` исключает повтор награды между
устройствами/аккаунтами. Ledger, баланс, XP, revision и аудит фиксируются одной
транзакцией под блокировкой аккаунта. Сетевая проверка проходит вне транзакции,
перед записью повторно проверяется действующая сессия. Сбой откатывает все эффекты.
Базовая сумма и версия политики сохраняются для будущих ретродоплат, но сам
provider поддержки и выплаты ×2/×3 ещё не реализованы.

- `GET /v1/me/progression` — собственный уровень/XP/баланс, привязка/challenge,
  последние 50 операций (награды и отрицательные траты); отсутствующий аккаунт прогресса создаётся с настоящими 0 XP,
  0 Искр и уровнем 1. Исторические строки продолжают храниться в журнале.
- `POST /v1/me/progression/ra/challenge` — username и web_key, новая проверка владения.
- `POST /v1/me/progression/ra/verify` — web_key, завершение своей проверки.
- `POST /v1/me/progression/ra/sync` — web_key и до пяти game IDs; сервер сам
  проверяет цели и рассчитывает суммы. Нет входа для Crates-выплат или raw XP.

Сетевые проверки ограничены общим ingress и постоянной паузой 15 секунд на ID.
Оболочка читает данные при входе/открытии профиля и каждые две минуты, обходит
известные ей RA-игры ограниченными пакетами. При ошибке запроса последний снимок
в памяти помечается устаревшим; смена локального владельца очищает его и отменяет
применение старого ответа. После перезапуска данные вновь читаются с сервера.
Траты/покупки в офлайне не обещаются. Нет SDK capability для mint.

## Расчёт поддержки ×2 и ×3 — 28 октября

Владелец выбрал **два уровня ×2 и ×3**; базовый заработок бесплатен (×1).
Цены, провайдер подтверждения и оплата пока не подключены. Capability
`support.balance_preview: 1` означает только чтение расчёта через существующий
`GET /v1/me/progression`, не покупку/активацию подписки или mint API.

`support_preview` имеет policy `support-preview-2026-10-v1`, state
`calculation_only`, `activation_available: false`, число допустимых наград,
сумму их `base_sparks`, уже начисленную сумму и два именованных `options`.
Для каждой исходной RA-награды сервер считает
`max(base_sparks × multiplier − sparks, 0)` и суммирует разницы.
`potential_balance = current balance + top_up`. Используется **весь журнал**
данного игрока, а не последние 50 строк истории. Траты не уменьшают базу,
XP не умножается. Баланс и расчёт читаются под одной блокировкой аккаунта,
согласованно с уже сериализованными начислениями/покупками.

Пример: заработано 1000 Искр, потрачено 250, доступно 750. Для ×2 доплата 1000,
итог 1750; для ×3 доплата 2000, итог 2750. Сам просмотр не выдаёт деньги,
не меняет XP/revision и не создаёт запись награды. Новый аккаунт с настоящим
нулевым журналом получает нулевой расчёт; отсутствие валидного ответа — недоступно.

Клиент проверяет владельца/ревизию, policy, два уникальных коэффициента,
целые неотрицательные безопасные числа и равенство current + top-up = potential.
Невалидный preview скрывается, валидный кошелёк сохраняется. При обновлении,
ошибке сети или незавершённой покупке preview не показывается; смена аккаунта
очищает данные и отсекает поздний ответ. Оболочка не считает доплату сама.

**Граница:** текущий журнал содержит одно исходное начисление на RA-награду,
выплат поддержки ещё нет. Перед включением активации необходимо добавить
неизменяемые per-reward квитанции доплат, highest granted multiplier, проверку
провайдера, атомарную выдачу разницы и учёт этих квитанций в preview. Повторы,
переход ×1→×2→×3, cancel/rejoin и out-of-order события должны проверяться на
реальном механизме выдачи. Наличие расчёта не закрывает эти требования #262.

## Оставшиеся условия

Реальный игрок должен добавить Web API key, подтвердить свою привязку и заработать
новую награду. Изолированные provider fixtures не заменяют этот живой сценарий.
Первые постоянные покупки сцен реализованы в [миграции 0008](purchases.md).
Активация/проверка поддержки и реальные доплаты, игровой контент и его права, reversal, полная пагинация истории, восстановление
привязки, усиленная политика #94 и gameplay-приёмка остаются открыты.
Установленная версия и результаты проверок фиксируются в PLAYER_PROFILE;
наличие этого документа не является заявлением о поставке на устройства.
