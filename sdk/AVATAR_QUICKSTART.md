# Персонаж TrainerOS в вашей игре

Игра получает уже собранного персонажа: тело, одежду, волосы, глаза и выбранные
цвета. Пользователь меняет внешность в профиле TrainerOS, а игра подписывается
на сохранённые изменения. Самостоятельно собирать части персонажа не нужно.

## Что нужно установить

- Запущенная TrainerOS с выбранным локальным профилем и установленным общим
  пакетом аватара. Revision 4 поставлена на Odin/Flip 27 октября 2026.
- Игра и оболочка работают на одном устройстве под одним пользователем.
  Подключение локальное; аккаунт и Lobby для своего аватара не требуются.
- Для примера ниже: Godot 4.7.2 Standard. В этой версии проверяются Compatibility
  и Mobile. Другой движок может использовать тот же [JSON-протокол](PROTOCOL.md).

Для разработки не нужны публикация в Crates, отдельный сервер или копирование
моделей в проект. Если TrainerOS недоступна, игра должна работать с собственным
анонимным персонажем/значком.

## Запустить готовый пример

Из корня этого репозитория:

```sh
godot --headless --path sdk/godot --editor --import --quit
godot --path sdk/godot
```

`godot` здесь — путь к установленному редактору Godot. На Windows можно указать
полный путь к `Godot_v4.7.2-stable_win64_console.exe`.

Окно показывает сохранённого Trainer. Кнопки запускают поддержанные действия.
С пакетом revision 5 доступны также эмоции, рты, сила выражения и разовые реакции.
Крупный план включается через Face close-up. [API выражений](AVATAR_EXPRESSIONS.md)
объясняет приоритет и плавные переходы; для revision 5 нужен обновлённый resolver.
Измените глаза/волосы в гардеробе профиля, сохраните и вернитесь в пример:
персонаж обновится. Cancel в гардеробе не меняет персонажа игры. Без оболочки
виден анонимный силуэт; кнопка Connect делает новое явное подключение.

Оболочка публикует endpoint в пользовательских данных. Клиент ищет его сам:

| Платформа | По умолчанию |
| --- | --- |
| Linux | `$XDG_DATA_HOME/traineros/platform-v1/endpoint.json`, иначе `~/.local/share/traineros/platform-v1/endpoint.json` |
| Windows | `%LOCALAPPDATA%/traineros/platform-v1/endpoint.json` |

Для отдельной development-сессии задайте `TRAINEROS_SDK_ENDPOINT` и оболочке,
и игре. Не зашивайте порт и token в код; не публикуйте содержимое endpoint.

Исходник примера: [avatar_demo.gd](godot/avatar_demo.gd), сцена:
[avatar_demo.tscn](godot/avatar_demo.tscn). Он ничего не сохраняет в профиле.

## Подключить свой Godot-проект

1. Скопируйте `avatar_client.gd` и `avatar_presenter.gd` из `sdk/godot` в
   `res://addons/traineros/`. Сохраняйте вместе версию исходников и сведения об
   их лицензии GPL-3.0-or-later. Модели и текстуры копировать не нужно.
2. Добавьте в сцену `Node3D` для персонажа и следующий скрипт. Замените app ID
   на стабильный ID своего проекта; разные проекты не должны делить один ID.
3. Разместите anchor на полу. Масштаб — метры, верх +Y, лицо смотрит вдоль +Z.
   Если игра использует -Z вперёд, поверните anchor на 180° вокруг Y.

```gdscript
extends Node3D
const Client = preload("res://addons/traineros/avatar_client.gd")
const Presenter = preload("res://addons/traineros/avatar_presenter.gd")
var client = Client.new()
var visual: Node3D

func _ready() -> void:
    client.app_id = "org.example.my-game.avatar"
    client.appearance_changed.connect(_appearance)
    client.unavailable.connect(func(_reason): _clear())
    add_child(client)
    client.connect_host()

func _appearance(description: Dictionary) -> void:
    var replacement = Presenter.from_descriptor(description)
    _clear()
    if replacement == null:
        return # Здесь покажите анонимный образ своей игры.
    visual = replacement
    add_child(visual)

func _clear() -> void:
    if is_instance_valid(visual):
        visual.clear_identity()
        visual.queue_free()
    visual = null
```

Это минимальная немедленная замена. В игре с ударом, прыжком или другим действием
сохраняйте **последний** description в pending и применяйте его после действия.
Отзыв личности и потеря соединения очищают образ сразу, вместе с pending.
Не откладывайте отзыв до конца раунда. Игровые коллизии и управление принадлежат
игре: добавление аватара не должно менять результат симуляции.

Presenter проверяет SHA-256 и размер файла перед загрузкой. Используйте `glb`
для персонажа с анимациями; `preview` предназначен для нейтрального превью Qt.
`visual.eye_height` задаёт высоту камеры. `visual.play_action("wave")` возвращает
false для неподдержанного действия. Список доступен в `description.actions`.
Не привязывайте код к числу MeshInstance3D: новая одежда или глаза добавляют части.

## Другой движок или только портрет

Для C++, C#, Rust, JavaScript и других клиентов последовательность одинаковая:

1. Прочитать локальный endpoint, открыть TCP к указанному localhost-порту.
2. Отправить `hello` с protocol 1, app ID и token. Каждое JSON-сообщение заканчивается
   переводом строки; ответы сопоставляются по `id`, события имеют поле `event`.
3. Проверить `capabilities["avatar.local"] == 1`, вызвать `avatar.subscribe`.
4. Из ответа `result.avatar` или события `avatar.changed.avatar` взять описание.
   Проверить SHA-256 и загрузить внешний GLB 2.0 средствами движка.
5. На `context.revoked`, `host.stopping` или EOF удалить личный образ и ожидающие
   обновления. Повторное подключение — отдельное решение для текущего профиля.

Точные поля и wire-примеры: [контракт аватара](AVATAR.md). Синхронные запросы
и загрузку большого файла не выполняйте каждый кадр. Дубликат `revision` можно
пропустить; путь к файлу не является постоянным ID игрока.

Для карточки используйте [Qt AvatarCards](qt/README.md) либо
`avatar_portrait.gd` в Godot. Последний файл требует `avatar_presenter.gd` рядом.
Он возвращает Texture2D после однократного снимка и освобождает 3D viewport.
При асинхронном снимке проверяйте, что профиль и revision всё ещё актуальны.

## Соперники и локальные гости

Своя модель не является моделью второго игрока. Для гостя/бота нужен анонимный
образ. Личность сетевого участника берётся из допущенной игровой сессии.

По существующему игровому каналу передавайте только `description.recipe`:
менее 1 КиБ, IDs частей, цвета, схема и хеш набора. На другой консоли
`avatar.resolve` собирает модель из её пакета. Файлы, локальные profile ID,
пути и endpoint/token по сети не передаются. Несовпадающий packRevision означает
анонимный образ до согласованного обновления пакетов, а не автоматическую загрузку.
Готовый помощник и ограничения: [peer recipe](AVATAR.md#peer-recipe-without-transferring-models).

## Если что-то не работает

| Симптом/ошибка | Действие разработчика |
| --- | --- |
| Нет endpoint / соединение закрыто | Оставить игру рабочей с анонимным образом; проверить, запущена ли оболочка под тем же пользователем |
| Нет `avatar.local` | Не вызывать методы аватара; текущая установка не предоставляет пакет/сервис |
| `no_profile` | Предложить выбрать Trainer в оболочке |
| `avatar_not_ready` при subscribe | Подписка уже действует: дождаться `avatar.changed`, не создавать цикл повторных запросов |
| `avatar_pack_mismatch` | Показать анонимного соперника; сравнить версии установленных пакетов |
| `avatar_busy` | Дождаться предыдущего resolve; объединять частые изменения в последнее |
| SHA-256 не совпал / Presenter вернул null | Не показывать старый образ как новый; очистить визуал, записать диагностическую причину без токенов |
| Лицо темнее в Compatibility | Обновить общий `avatar_presenter.gd`; адаптация линейных vertex colors находится в SDK |
| После нового костюма сломалась игра | Проверить предположения о числе/индексах mesh; загружать всю сцену |

Перед выпуском проверьте запуск без TrainerOS, первое подключение, Save/Cancel,
обновление во время действия, отзыв профиля, повторное подключение, локального
гостя и несовпадающий пакет соперника. Моргание/взгляд и физика ткани сейчас
не входят в API. Авторские исходники и происхождение ассетов — отдельные от
клиентского кода [материалы](../assets/avatar/README.md).
