кадры, физика и Lobby остаются у своих владельцев. Account/refresh/grant tokens
игре не выдаются. Обычная локальная игра работает без входа и этого сервиса.

## Маршрут игры

1. `account.get` должен вернуть `signed_in`. Вход выполняется в Settings оболочки.
2. `play.rules {}` возвращает зарегистрированные неизменяемые правила.
3. `play.open {ruleset_id}` открывает доступ для данного SDK-соединения.
   Результат: ruleset, expires_at, trust. В этой версии trust — `peer_confirmed`.
4. Хозяин делает `play.create`: mode `individual`, seats `[1,1]` / `[1,1,1,1]`
   либо mode `teams`, seats `[2,3]`. Всего 2–16 игроков; команды по 2 или 3.
   Хозяин занимает сторону 0. Сервер выдаёт match.id; игра передаёт его приглашённым
   через существующий Network/Lobby. Не публикуйте ID открытого матча: его знание
   позволяет запросить свободное место. Это отдельный явный шаг вступления.
5. Каждый участник сам делает `play.join {match_id,side}`. Хозяин не может
   записать чужой Player UUID вместо его согласия. После заполнения всех мест
   хозяин вызывает `play.start {match_id}`; состав и стороны замораживаются.
6. Каждый присылает **всю одинаковую карточку** через `play.submit`:
   `{match_id,scores:[{side:0,values:[3,4,2]},{side:1,values:[4,5,3]}]}`.
   В команде одна карточка общего мяча, не сумма личных ударов всех участников.
   Чередование ходов исполняет игра; этот валидатор не проверяет физику/порядок ходов.
7. `play.get {match_id}` возвращает текущее решение, состав, состояния заявок,
   проверочных jobs и историю решений. Intake receipt не означает verified.
   `confirmed` возникает только после проверки всех карточек и согласия всех.
8. `play.board` читает общую таблицу; `play.stats` — собственные матчи, победы,
   поражения, ничьи и уникальных побеждённых; `play.history` — последние 50 матчей.
   `play.cancel` доступен хозяину до старта. После старта отказ от ответа оставляет
   матч неподтверждённым. По истечении окна сервер больше не принимает заявки.

Методы create/join/start/cancel/submit/get/history/stats принимают оболочку
`{operation_id:UUID,payload:{...}}`. Для get/history/stats UUID не создаёт запись.
Для мутации игра **сохраняет UUID и payload до отправки**. Повтор с тем же UUID
и телом даёт прежний receipt; другое тело — `operation_payload_conflict`.
Потерянный ответ означает неизвестный исход. После явного переподключения под тем
же Player и открытия тех же правил можно повторить исходную команду. Метод
`play.get` позволяет прочитать уже известный матч. Автоповтора/смены владельца нет.

Пример Python (сетевой timeout не меньше 20 секунд):

```python
from traineros import Client
import uuid

client = Client("org.example.game", timeout=20)
client.play_open("traineros.scorecard-demo.v1")
operation = str(uuid.uuid4())  # сохранить вместе с payload перед мутацией
result = client.play("create", {"mode":"individual", "seats":[1,1]}, operation)
match_id = result["match"]["id"]
```

[Исполняемый пример](examples/scorecard_demo.py) проходит полную цепочку на 2–16
отдельных host endpoints; при пяти игроках дополнительно проверяет 2 против 3.
Он использует только явно названный **демонстрационный** ruleset, не результаты
Pocket Golf. Производственные игры ещё должны привязать реальные версии правил
и контента, точки старта/завершения и свой экран общей таблицы.

## Правила таблиц

`play.board {mode:"individual"|"teams",kind:"records"|"wins",limit:20,offset:0}`.
Необязательные `revision` (десятичная строка) и `around` (Player UUID).
Ответ содержит items, revision, offset, next_offset. Следующую страницу запросить
с полученной revision; `stale_revision` требует начать чтение заново. Limit 1–50,
offset до 10000. Around выбирает первый подходящий состав, содержащий игрока.

- Ключ: неизменяемый ruleset, включающий игру/контент/метрику, плюс mode/kind.
  Разные поля, версии правил и личные/командные рекорды не смешиваются.
- Records: лучший полный результат игрока либо точного состава команды.
  Метрики целые; направление задаёт оператор (`asc` или `desc`).
- Wins: число единоличных побед субъекта. Равенство лучших значений в матче —
  ничья, не дополнительные победы. Места таблицы — 1,1,3; UUID лишь стабилизирует
  порядок равных строк, не меняет место. Члены победившей команды получают по
  победе в личной статистике; командная таблица хранит одну строку состава.
- Противоречащая карточка делает матч disputed и **сразу** убирает все его
  результаты из таблиц/статистики, даже если worker ещё не обработал очередь.
  Источники/решения сохраняются. Администратор может аннулировать матч.
- Общая таблица доступна для чтения публично, без локальных отдельных рекордов.
  Соревновательная сила/Elo, сезоны, турниры, экономика и награды не включены.

## Доверие и жизненный цикл

Валидатор scorecard.v1 проверяет стороны, число сегментов, целочисленные диапазоны,
вычисляет суммы, места, победы/ничьи и требует все подтверждения. Он **не доказывает**
прохождение трассы, отсутствие читов/ботов или независимость участников. Статус
`confirmed` и trust `peer_confirmed` не равны серверному воспроизведению игры.
Такие таблицы нельзя незаметно использовать для будущих verified-наград.

Grant привязан к серверной сессии, Player и ruleset, живёт до двух часов, хранится
только в памяти host. Один открытый ruleset на SDK-соединение; новое play.open
отзывает прежний. Disconnect/смена Trainer отзывают grant best effort и прекращают
callbacks; потерянный revoke ограничен TTL. Отзыв account session проверяется
сервером на каждом запросе. Push revocation в оболочку пока отсутствует.

App ID — локальное имя, **не доказательство publisher/build identity**. Backend
не объявляет grants аттестацией установленной игры и не даёт им финансовых прав.
При необходимости более сильной категории понадобятся доверенный admission
конкретного билда/режима и отдельный игровой валидатор.

Один запрос одновременно на SDK-соединение; другой получает play_busy. Host
разрешает только фиксированный набор методов, не произвольный HTTP proxy.
Объём тела до 16 KiB, карточки до 16 сторон × 18 значений. Матч: 2 часа на сбор,
после Start — 2 часа на результат. Обновлять состояние достаточно раз в 2–5 секунд.
Возможны account_busy, sign_in_required, play_not_open, grant_expired, match_expired,
roster_incomplete, side_full, roster_frozen, match_closed, rate_limited.
Все незавершённые заявки остаются без победы, а не превращаются в поражение.

Проверка 16 backend-участников не является проверкой FPS/сетевой физики 16 игроков.
Портативки этим проходом не проверяются и не обновляются.
